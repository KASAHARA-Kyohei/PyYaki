# PyYaki 要件定義

状態: 初期設計案 / 作成・技術調査日: 2026-10-30 / 名称更新: 2026-10-31 / コード未実装

## 1. 目的と用語

PyYakiは、共通のPython業務ロジックとHTML/CSS/JavaScriptのUIから、WindowsデスクトップアプリとWebアプリを作るOSSフレームワークを目指す。

表示名はPyYaki（鯛焼きにかけた名称）、パッケージ・Python import・CLI・JavaScript SDKは`pyyaki`とし、2026-10-31に利用者が採用を承認した。

「Pythonだけ」は、利用者がRust/Cargoやネイティブビルド環境を扱わず、Pythonをアプリケーション言語にできることを指す設計案とする。自由なUIにはHTML/CSS/JavaScriptを使用する。PythonだけでUIも宣言する仕組みはMVP対象外であり、この表現を「HTML等の知識が一切不要」という保証には使わない。

- **必須**: 利用者が指定した要件。設計案によって緩和しない。
- **提案**: 本書のMVP範囲、対応環境、数値目標など。採用済みではない。
- **公式確認**: 一次資料に機能が記載されている状態。PyYakiでの動作検証とは異なる。
- **要検証**: 試作・実機確認が必要。現在、性能や互換性の実測結果はない。
- **単一exe**: Python、アプリ、UI、必要なWebView2を含む配布ファイルが1つ。ユーザー回答により必須。実行時のユーザー領域への展開方式は提案であり、無展開・完全インメモリ実行を保証しない。
- **画面**: Rustによる起動画面、HTMLのアプリ画面、Python接続後の操作可能画面を区別する。

要件と受入条件の正本は本書、技術選定とADR候補は[architecture.md](architecture.md)、APIの正本は[api-design.md](api-design.md)とする。

## 2. 利用者と対象環境の提案

| 区分 | MVP提案 | 留意点 |
| --- | --- | --- |
| アプリ開発者 | PythonとテキストUI資産を編集する人 | Python環境は必要。Rust、Cargo、Node.jsは基本構成で不要 |
| Windows利用者 | Windows 11 x64、標準ユーザー、ローカルディスク | Pythonの別途導入不要。Windows 10、ARM64、x86、Windows Serverは将来評価 |
| Python | CPython 3.14通常GIL版を最初の検証候補にする | パッチ版は配布前に固定。free-threaded版、PyPyはMVP対象外 |
| Windowsビルド | Windows 11 x64 + 対応する開発用CPython | 他OSからのWindowsクロスビルドはMVP対象外 |
| Web開発 | 対応CPython上のFastAPI/Uvicorn、主要なChromium系ブラウザ | macOS/LinuxはWeb開発だけを検証対象とする案。Safari/Firefoxは後続評価 |
| Web実行 | Pythonサーバー + ブラウザ | ブラウザ内Python実行ではない。静的ホスティングだけでは動作しない |

これはサポート保証ではなく、最初の実装・検証範囲の提案である。OS、Python、WebView2の正確な最低版はADR-007の検証後にサポート表へ固定する。

## 3. 機能要件と受入条件

| ID | 必須要件 | MVPでの受入条件 |
| --- | --- | --- |
| FR-01 | PythonとUIコードのWindows/Web共通化 | 同一のPython公開コマンドと同一のHTML/CSS/JS資産で、入力・応答・イベント・エラーの共通シナリオが両方で動く。通信アダプターはフレームワークが切り替える |
| FR-02 | 自由なHTML/CSS/JavaScript UI | ローカルの外部CSS、ES modules、画像、フォントが利用できる。特定のUIライブラリ・CDN・Node.jsを必須にしない |
| FR-03 | Rust製GUIホスト | ウィンドウ管理とPython非依存の起動経路をRustで提供する。HTML描画はWindowsのWebView2が担当し、RustがHTMLレンダラーを自作する意味ではない |
| FR-04 | Python初期化前の画面表示 | Pythonの起動を意図的に5秒遅延しても、Rustの描画と閉じる操作が先に動く。通常の起動ではHTMLシェルの描画確認後にPythonを起動する提案。空のウィンドウ枠だけを合格にしない |
| FR-05 | `pip install pyyaki` | 対応環境の新規venvへwheelだけで導入できる。Rust/Cargo/C/C++コンパイラ不要。Windowsの`pyyaki`はPythonを先に初期化しないネイティブコマンドとする |
| FR-06 | `pyyaki dev` | ブラウザ向けサーバーを既定で`127.0.0.1`に限定して起動。UI変更を再読込し、Python変更時は開発サーバーを再起動する。ポート競合を説明できる |
| FR-07 | `pyyaki run` | Windows上でGUIホストを直接起動し、開発用venvのPythonワーカーへ接続。HTTP/WebSocket待受を作らず、Python importが失敗してもGUIに原因を表示する |
| FR-08 | `pyyaki build windows` | Rust不要で依存ファイルを含む**単一exe**を生成。配布先でPython/WebView2未導入・ネットワーク切断・標準ユーザーの条件でも起動する。フォルダー/ZIPのみの成果物は要件を満たさない |
| FR-09 | ビルド済みランチャー | フレームワークのリリースでコンパイルしたホストを再利用する。利用者のアプリごとにRustをコンパイルしない。版とハッシュの不一致をビルド時に検出する |
| FR-10 | Webアプリとして実行 | 同一アプリをASGIアプリとして公開できる。2つのブラウザセッションで状態とイベントが混線しない。インターネット公開にはアプリ側の認証・認可を要求する |
| FR-11 | AIがUIを編集しやすい | UIファイルをPython/Rustから独立させ、命名の安定したDOM、通信SDK、公開コマンドの契約を文書化。生成済み巨大ファイルだけを編集対象にしない |

## 4. 非機能要件

| ID | 必須要件・方針 | 受入条件・限界 |
| --- | --- | --- |
| NFR-01 | 高速起動 | 後述の4指標を初回展開・キャッシュ利用別に計測。数値は暫定目標で、未達を隠さない |
| NFR-02 | 管理者権限不要 | 対応する標準ユーザー環境でUAC昇格、サービス登録、マシン全体のPATH変更、ランタイムインストールなしに実行。企業の実行許可を保証する意味ではない |
| NFR-03 | オフライン実行 | 単一exeの初回起動も外部取得不要。UI資産・依存DLL・Python・Fixed Version WebView2を同梱する案。オフラインビルドは必要資材を事前準備した場合に対応 |
| NFR-04 | Windowsでlocalhostサーバー不使用 | `run`と配布exeのアプリ通信・UI配信にTCP/UDP待受を使わない。WebView2内部の資産要求処理と匿名パイプで完結。`dev`はブラウザ用サーバーなので対象外 |
| NFR-05 | 企業プロキシへの依存を最小化 | 内部RPCとUI資産配信をHTTPネットワークから切り離す。無効なプロキシ/PAC設定でもローカル画面とRPCが動く。アプリ独自の外部通信やOS管理処理は別途評価 |
| NFR-06 | 安全な公開API | 明示登録コマンド、入力検証、origin検査、CSP、通信量制限を実装。任意import/eval/シェルをJSへ公開しない |
| NFR-07 | 障害時も応答する画面 | 展開・Python初期化・重いimportをGUIスレッドで実行しない。失敗・タイムアウトをGUIで通知し、閉じる操作で子プロセスを回収できる |
| NFR-08 | 配布の追跡可能性 | バージョン、成果物ハッシュ、依存一覧、SBOM、ライセンス通知、ビルド元コミットを記録。署名・来歴の検証手順を用意 |
| NFR-09 | ネイティブ依存の明確な範囲 | 対応wheelがあるパッケージを対象に実機検証。全PyPIパッケージ対応を約束しない。未対応依存をサイレントに除外しない |
| NFR-10 | 実行制限との共存 | Defenderを有効にして評価。署名・企業向け許可リスト情報を提供する。AppLocker/WDAC/Smart App Controlの回避や無効化を行わない |
| NFR-11 | データの分離 | 配布exeの配置先は読取専用でもよい。展開キャッシュ、WebView2プロファイル、アプリデータ、ログをユーザー領域で分離。削除対象に業務データを含めない |

## 5. 起動速度の測定仕様

### 5.1 時点と指標

| 時点 | 定義 |
| --- | --- |
| t0 | 外部計測器が`CreateProcess`を呼ぶ直前。Explorer起動は別の体感評価とする |
| t1 | Rustの起動画面に内容が初めて描画され、閉じる操作が応答可能になる |
| t2 | アプリのHTMLシェルが最初に描画される。静的な見出し等があり、空白ページではない |
| t3 | Pythonワーカーがimport・登録を終え、hello/welcomeが完了する |
| t4 | JSから最初のPythonコマンドを呼び、結果が画面に描画される |

`T_native=t1-t0`、`T_shell=t2-t0`、`T_backend=t3-t0`、`T_interactive=t4-t0`を個別に記録する。展開・ハッシュ検証・WebView2初期化・Python初期化・アプリimportも内訳として残す。`pyyaki run`ではコマンドのネイティブ起動をt0とし、Pythonラッパーを計測の外に隠さない。

### 5.2 暫定の性能予算

以下は軽量な基準アプリに対する**提案値、未測定**。最初の試作結果によりADR-009で更新する。

| p95目標 | 展開済み・プロファイルあり | 初回展開・プロファイルなし |
| --- | --- | --- |
| T_native | 300 ms以下 | 500 ms以下 |
| T_shell | 1.5秒以下 | 10秒以下 |
| T_interactive | 2秒以下 | 12秒以下 |

基準案はWindows 11 x64、4コア以上、メモリ16GB、SSD、AC電源、Defender既定設定。CPU機種、OSビルド、依存版、exe容量を報告に記録する。T_backendは値と内訳を報告し、アプリ固有の初期化時間をフレームワークの保証に含めない。

### 5.3 実験手順

1. releaseビルドの同一exeと同一アプリで比較する。Pythonを5秒遅延する試験も別に実行する。
2. 初回展開は毎回新しいキャッシュとプロファイルで30回、展開済みは30回以上測定し、p50/p95、最大値、サンプル数と失敗件数を記録する。
3. OSページキャッシュの温冷とアプリ展開キャッシュの有無を混同しない。再起動後の測定を別群として10回以上収集し、少数標本のp95を保証値にしない。
4. ホストは単調時計、Python/JSは局所的な所要時間を記録。クロックの異なる時刻を直接減算せず、ホスト受信時点と外部トレースで対応づける。
5. HTML描画マーカーはrequestAnimationFrame等で通知する案とし、真の画面提示との差をETW/WPRや画面録画で確認。DOMロードだけを初描画と見なさない。
6. Defender有効、MOTW付きダウンロード、長い日本語パス、読取専用配置、ネットワーク切断、無効プロキシでも測定する。性能測定のために保護機能を無効化しない。
7. RSS/Private Bytes、全プロセス数、CPU使用量、exe/展開後容量も記録する。Rustホストだけのメモリ値を全体値にしない。

## 6. MVPで実装する範囲

単一ウィンドウ、静的UI資産、明示登録した非同期Pythonコマンド、JSON要求/応答、セッション限定イベント、Web向け開発サーバーとASGI公開、Windowsでの実行、単一exeビルド、初回展開、エラー表示、計測を対象とする提案。

単一exe、ランタイム未導入端末での初回オフライン実行、Rust不要のpip導入、Python初期化前描画は、後回しの拡張機能ではなく**MVP公開の合格条件**とする。Fixed Version同梱はこの条件を満たすための技術提案であり、要件そのものとは区別する。困難な場合はゲート不合格として記録し、利用者の合意なしにフォルダー配布へ変更しない。

## 7. MVP対象外

- macOS/LinuxのネイティブGUI、Windows 10/ARM64/x86、他OSからのWindowsクロスビルド。
- ブラウザ内Python/WASM、サーバー不要のWeb実行、PWAの完全オフライン動作。
- PythonによるUI DSL、独自ウィジェット体系、React/Vue等の統合ツールチェーン。
- マルチウィンドウ、トレイ、通知、ネイティブファイルダイアログ、任意ローカルファイル公開、汎用シェルAPI。
- PyO3のプロセス内埋め込み、free-threaded Python、ユーザー作成Rustプラグイン。
- sdistの自動コンパイル、GPU/CUDA同梱、ドライバー/サービスが必要な依存、全Python依存の自動検出保証。
- 自動更新、差分更新、MSI/MSIX/Store配布、管理者ポリシーの変更、コード署名証明書の自動取得。
- Webの認証基盤、複数ワーカー間の状態同期、イベントの永続化・再送、任意の長時間ジョブ管理。

## 8. 前提と残る確認

単一exeを必須とする点と、名称PyYaki/`pyyaki`の採用は確認済み。[名称調査結果](../README.md)は公開時に再確認する。Windowsの具体的な対応版、性能予算、Python minor版、OSSライセンス、公開先、PyPIへの実際の登録可否は提案または未確認である。未決事項は正式採用前に確認し、[ADR候補](architecture.md#8-adr候補一覧)へ記録する。外部への公開やOSSライセンスの正式採用はこの文書作成には含めない。
