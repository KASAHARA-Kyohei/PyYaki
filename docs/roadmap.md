## 2. 推奨する最初の実装タスク

**最初は「Pythonを待たない単一exeのWindows起動試作」を作る。** フルAPIやUI DSLの実装より先に、最も不確かな起動・配布要件を検証する。

1. Windows 11 x64、CPython 3.14通常GIL版の検証マトリクスを固定し、クリーンVMを用意する。パッチ版・WebView2版は公式配布物のハッシュと再配布条件を確認して記録する。
2. PythonへリンクしないRustホストで起動画面を描画する。主スレッドで閉じる操作が動くことを確認する。
3. 仮の小さなUI、固定WebView2、埋込Pythonをペイロードへ入れ、1つのexeに組み立てる。起動画面の描画後に作業スレッドで検証・展開する。
4. localhostサーバーなしでHTMLシェルを表示し、描画マーカーを確認してからPythonを生成する。
5. Pythonの初期化/アプリimportを意図的に5秒遅らせ、Rust画面とHTML画面の応答性を記録する。Pythonが失敗・クラッシュしても閉じられるか試験する。
6. 専用パイプで1回だけのping/pongを行い、stdoutへ大量に出力しても壊れないことを確認する。まだ公開API全体は作らない。
7. 初回・展開済みの`T_native / T_shell / T_backend / T_interactive`と容量を測定する。外向き通信とアプリの待受ポートをトレースする。
8. 最小Windows wheelからネイティブ`pyyaruki.exe`をpip配置し、`run`が先にPythonを初期化しないことを確認する。署名前後でexeのペイロード検証も行う。

この結果をもとに、tao/wry継続かTauri/PyTauri再利用か、圧縮方式、origin方式、キャッシュ検証方式、性能予算をADRへ記録する。実装の容易さだけで必須条件を削らない。

## 3. G2の実装順序

| 順序 | 作業 | 完了の証拠 |
| --- | --- | --- |
| 1 | コマンド名・型・JSONスキーマ・エラー・制限値の定義 | 実行コードから独立した契約ケース |
| 2 | PythonのApp/Context/ディスパッチャーと起動・終了フック | 単体の型検証/セッション分離試験 |
| 3 | Rust/Pythonパイプの制御面とワーカー監視 | 部分read/write、長さ不正、クラッシュ、終了試験 |
| 4 | JS SDKのready/invoke/on | ready前、同時呼出し、取消、期限、切断の試験 |
| 5 | FastAPI/Uvicornアダプターと`dev` | 同じ契約ケース、cookie/nonce/origin拒否、2セッション試験 |
| 6 | 同一UIと業務コードで`dev`/`run`を実行 | コードを複製しない共通例と操作結果 |

制約とAPIは[api-design.md](api-design.md)を正とし、アダプターごとにエラーコードやタイムアウトが分岐しないようにする。
