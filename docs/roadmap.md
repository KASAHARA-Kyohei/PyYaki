### 1.1 Macでの先行開発とWindows検証の扱い

最初のMac試作の到達点とCPython 3.14通常GIL版の使用は2026-10-31に利用者が承認した。実装開始後は次の順序で進める。Windows確認へ移る具体的な時期は未決であり、「ある程度」を全機能完成と解釈しない。

1. MacでCPython 3.14通常GIL版を使い、JSON契約、共通Pythonディスパッチャー、JS SDK、最小UI、Web経路を小さく試作する。最初の到達点はHTMLからPythonコマンドを呼び、結果・エラーを表示でき、非同期処理中もUIが応答すること。完成条件はrequirements.mdの6.1を正とする。G2の一部を先行するが、Windows/Web共通動作の合格にはしない。
2. Windows確認へ移る時点で手元の端末のOS・CPUを確認し、G1の最小試作をビルド・実行する。対応候補に適合しない場合は、検証環境を利用者に確認する。
3. G1の結果を反映してからWindows依存部分を作り込み、両環境でG2を完了する。続いてG3/G4で配布・性能・安定性を評価する。

Windowsの先行描画、WebView2、匿名パイプ、ネイティブCLI、単一exe、Defenderとの共存は、Macでの成功から成立を判断できない。Windows固有の技術候補はWindows確認まで未採択とし、変更時の手戻りをリスクとして残す。Macでの測定値をWindowsの起動目標の達成証拠に使わない。

## 2. Windowsで最初に行う実装・検証タスク

**Windows確認へ移ったら、最初に「Pythonを待たない単一exeのWindows起動試作」を作る。** Windows依存機能を作り込む前に、最も不確かな起動・配布要件を検証する。

1. Windows 11 x64、CPython 3.14通常GIL版の検証マトリクスを固定し、クリーンVMを用意する。パッチ版・WebView2版は公式配布物のハッシュと再配布条件を確認して記録する。
2. PythonへリンクしないRustホストで起動画面を描画する。主スレッドで閉じる操作が動くことを確認する。
3. 仮の小さなUI、固定WebView2、埋込Pythonをペイロードへ入れ、1つのexeに組み立てる。起動画面の描画後に作業スレッドで検証・展開する。
4. localhostサーバーなしでHTMLシェルを表示し、描画マーカーを確認してからPythonを生成する。
5. Pythonの初期化/アプリimportを意図的に5秒遅らせ、Rust画面とHTML画面の応答性を記録する。Pythonが失敗・クラッシュしても閉じられるか試験する。
6. 専用パイプで1回だけのping/pongを行い、stdoutへ大量に出力しても壊れないことを確認する。既存の共通APIを使い、配布の最小検証のために公開APIを拡張しない。
7. 初回・展開済みの`T_native / T_shell / T_backend / T_interactive`と容量を測定する。外向き通信とアプリの待受ポートをトレースする。
8. 最小Windows wheelからネイティブ`pyyaki.exe`をpip配置し、`run`が先にPythonを初期化しないことを確認する。署名前後でexeのペイロード検証も行う。

この結果をもとに、tao/wry継続かTauri/PyTauri再利用か、圧縮方式、origin方式、キャッシュ検証方式、性能予算をADRへ記録する。実装の容易さだけで必須条件を削らない。
